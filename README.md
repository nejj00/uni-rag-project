# RAG System — Recipes & ACL Anthology

A two-part Retrieval-Augmented Generation system built for the *Information Retrieval & Search Engines* course. Part 1 implements a RAG pipeline from scratch over a recipe dataset using classical TF-IDF retrieval; Part 2 extends it with dense embeddings, long-document handling, and query augmentation over a corpus of ACL Anthology papers.

Full write-up and experiment results: [`presentation/IRSE-slides-r1035493.pdf`](presentation/IRSE-slides-r1035493.pdf).

*All generation — answers, query rewrites, and HyDE paragraphs — was produced by `Mistral-7B-Instruct-v0.2` throughout both parts.*

## Part 1 — Cooking Recipes

Classical, word-level RAG pipeline:

- **Preprocessing** — lowercasing, tokenization, stopword removal, lemmatization
- **Retrieval** — `TfidfVectorizer` (uni+bigrams) with cosine similarity, dynamic top-k cutoff (stops on a >50% score drop-off, k ∈ [2, 10])
- **Document representation** — fields weighted by relevance (name ×3, ingredients ×2, temperature ×2, tags/description ×1); step text excluded as noise
- **Query handling** — spell-correction fallback for out-of-vocabulary queries
- **Generation** — `Mistral-7B-Instruct-v0.2` (4-bit quantized) answering from retrieved recipes only

**Findings:** field-repetition weighting raised MAP from 0.372 → 0.500. The LM reliably grounds answers in retrieved context (refuses out-of-domain questions, reasons across multiple recipes) but inherits TF-IDF's blind spots — negation, synonyms, and compositional queries all cause retrieval failures no amount of prompt engineering fixes.

## Part 2 — ACL Anthology

Extends the pipeline with neural retrieval and long-document strategies, evaluated on a corpus of NLP papers:

| Component | Approach |
|---|---|
| Embeddings | `sentence-transformers/all-MiniLM-L6-v2` over title + abstract + authors |
| Long documents | **Chunking** (200-word windows, 50-word overlap, max-pooled per document) and **Hierarchical selection** (FAISS pre-filter → weighted per-section similarity) |
| Query augmentation | **Query rewriting** (LLM-generated paraphrases, fused by vote) and **HyDE** (retrieve using an embedded hypothetical answer instead of the raw query) |
| Prompting | Inline citation formatting, uncertainty admission, prompt-injection resistance |

### Retrieval results (MAP)

| Strategy | MAP | Notes |
|---|---|---|
| Part 1 — TF-IDF | 0.500 | word-level baseline |
| Part 2 — Dense (baseline) | 0.520 | no query augmentation |
| Part 2 — Query rewriting | 0.505 | fusion by vote across 3 rewrites |
| Part 2 — HyDE | 0.535 | using paragrpah generated by LM as query |

There is a caveat about the Query rewriting and HyDE - the results are higly dependant on the quality of the rewriten queries and the generated paragraph, it is quite unstable and can change from run to run.

## Quick Start

Requires a CUDA-capable GPU.

```bash
chmod +x setup.sh part_1/run_part1.sh part_2/run_part2.sh
./setup.sh                  # creates .venv, installs dependencies
source .venv/bin/activate

cd part_1 && ./run_part1.sh # downloads data, runs the full RAG pipeline
cd ../part_2 && ./run_part2.sh
```

Each pipeline downloads its own dataset on first run and writes retrieval/generation/evaluation results to `results/`. See [`readme_setup.md`](readme_setup.md) for full configuration options and time estimates.

## Key Takeaways

1. Retrieval quality bounds answer quality — a strong LM cannot compensate for weak retrieval.
2. TF-IDF has fundamental semantic limits (synonyms, negation, compositional queries); dense retrieval helps but doesn't solve all of them.
3. Long documents and query ambiguity require targeted architectural choices (chunking, hierarchical scoring, query rewriting/HyDE) rather than a single universal fix.
